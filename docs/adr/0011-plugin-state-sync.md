# ADR-0011: Plugin state syncs as a content-addressed snapshot, announced by hash

- **Status:** Accepted
- **Date:** 2026-11-15
- **Deciders:** Chad

## Context

Parameter sync (#12) gives two people the same knob values, but many plugins keep part of what makes their sound outside their parameters: Serum 2's LFO shapes, modulation and wavetables, the loaded preset, embedded or referenced samples. Some plugins also change parameters on a preset load without telling the host. PLG-6 asks for this part to sync "by sending the plugin's saved state".

A host cannot see inside a plugin's saved state. It can only ask the plugin for all of it (VST3 `IComponent::getState` and `IEditController::getState`, which JUCE wraps as `getStateInformation`) and give all of it to another copy. It cannot tell what changed, merge two changes, or remove a file path from it. VST3 offers `setDirty` as a hint that the state changed, but nothing obliges a plugin to call it. State calls must be made on the main thread, and a state can be megabytes.

Issue #13's spike (`spikes/plugin-params`, [`README-STATE.md`](../../spikes/plugin-params/README-STATE.md)) built this between members with a test VST3 and measured it. On Windows it then measured 28 real plugins (finding 11) and ran the checklist by hand with Serum 2, FabFilter Pro-Q 3 and Sylenth1 (findings 12 to 14). On a Mac it measured 18 more (finding 15), and with Pro-Q 3 it ran two people editing at the same moment on two machines with two versions of the plugin (findings 16 to 18), then repeated it with the fixes and with FabFilter Pro-L 2 (findings 19 and 20). Back on Windows, a knob held while someone else's preset arrives kept the knob and took the rest of the preset, with Pro-Q 3 and Serum 2 (finding 21).

Serum 2 added two facts the test VST3 could not: every state it loads silences it for about 4 seconds, and it stores an imported wavetable as a path the host cannot see, then shows its own Missing Files dialog when the file is gone. Pro-Q 3, an effect, loads a state in 0.1 ms with no audible gap, and its display range, a view setting, travels in the state. Sylenth1 does not report a preset's parameters to the host, and hints before its state holds the new preset.

At first every knob turn in all three loaded a state on the receiver. That was the spike's wire format rounding parameter values (finding 14). With values sent exactly, a knob turn left both copies saving the same bytes, and nothing loaded.

Between a Windows PC and a Mac, two people editing Pro-Q 3 at the same moment ended on the same state every time: different bands both kept, the same band won by whoever let go last, a preset won whole. Pro-Q 3 3.2.7.0 and 3.2.9.0 loaded each other's states. But one drag was undone on both machines: a state read halfway through it was announced with the parameters from after it, and the receiver sent the halfway values back as the plugin's own silent change (finding 18, a spike bug). With the fix, the same drag stayed on both machines (finding 19). Three plugins on the Mac keep their whole state in the controller state.

With Pro-L 2, two presets clicked 0.4 s apart ended as a mix on both machines: the first preset's name with the second's parameter values (finding 20). A preset loaded in the plugin's own browser travels in two pieces, its parameters at once by parameter sync and its state when it is still, and the pieces won separately. With Serum 2, a click in the receiver's window seconds after it loaded a preset sent its saved-back version of that preset back, which replaced the sender's and once showed the previous preset's name on both copies (finding 21).

## Decision

- **What travels.** A plugin's state is the component and controller states as raw bytes (both: some plugins keep everything in the controller state), named by the SHA-256 of those bytes, like samples (ADR-0008). Members announce a new state by its hash in an operation in the ordered log (ADR-0004), so a late joiner gets it. The bytes go only to members whose own plugin does not already save that hash, as chunked, resumable binary transfers like samples (`spikes/sample-transfer`), never ahead of live parameter changes.
- **Who wins.** A plugin's state is one value: the newest announcement wins as a whole. There is no merging inside a state. A state from someone else that arrives while a change here has not gone out yet replaces it: it loads once nobody here holds a control, and the parameters changed here since its sender read it, the held one included, are set back on top. A person turning a knob while another member changes the preset keeps the knob; everything else follows the preset (decided 20 November 2026). A hidden edit here that had not gone out is lost to it, and the person is told (decided 21 November 2026). A copy never answers an incoming state by announcing its own (PLG-10), during the settling time or after it: a click in the plugin's window counts as an edit only if something the person did changed the state (finding 21; not built in the spike). A preset change travels as one unit: the parameter changes a plugin makes with nothing held while its state changes go inside the state's announcement, under its stamp, not ahead of it by parameter sync, so two presets at the same moment cannot mix (finding 20; not built in the spike). Nothing is locked: each member sees which plugin the others have up, whether its window is open and what they are touching (LOB-10), as two people at one synth would, and loading a preset while the other turns a knob is their call.
- **Parameters keep their own order.** A state carries its sender's parameter values and their stamps from when it was read. After loading one, a parameter known to have changed since is set back; a parameter the loaded state holds differently from its sender's snapshot was changed silently by the plugin, counts as written with the state, and is sent on as a parameter change.
- **Finding changes.** In layers: the plugin's hints (`setDirty`, a restart, a burst of parameter reports that change nothing), the mouse let go in the plugin's window, and polling while the window is open, limited to a small share of the main thread and skipped for plugins whose state changes with nothing done. A change is announced once the state has been still for a short time, with bytes and parameter values read together after the parameters are still, for every plugin. (A further limit, that a loaded state's value never wins over a newer change its own sender made to the same parameter, was considered and not built: it would also hide real silent changes, and reading bytes and parameters together removes the stale value it guarded against.)
- **Loading as little as possible.** A load can interrupt the receiver's sound for seconds, so a member does not load a state for a change that parameter sync already carried. Parameter values travel exactly, bit for bit, so that such a change leaves both plugins saving the same bytes and the hash comparison skips the load. A member does not load a burst of states one after another (Serum 2 refused some loads that came too close together), and retries a refused load with the newest state once the plugin has settled.
- **Reading after a hint.** The state is read when a hint arrives and again shortly after, since a plugin can hint before its state holds the change.
- **Loading.** Never while someone on that machine holds a control. Every load is read back and classified (loaded exactly, saved back differently, loaded with different parameters, not loaded), and the last two are shown. A load that changes nothing because the plugin already held that content, with every parameter equal to the sender's, is not a refusal; between versions this is common. Changes during a short settling time after a load are not announced unless a person did something (moved a parameter, or let go of the mouse in the plugin's window, which the host must see on every platform: on macOS that means asking AppKit, not JUCE). A host without that signal learns per plugin whether it rewrites its state after a load and keeps the settling time only for plugins that do.
- **File paths inside a state** are the plugin's own data. The host detects paths a state names that are missing on this machine and warns; it does not rewrite the state or send the files. This is an exception to "a local file path never goes over the network", limited to opaque plugin state. The host's search sees only plain-text paths and missed Serum 2's; some plugins warn the person themselves. Sending the files is #117.

## Alternatives considered

- **Send the state on every change, with no hash comparison.** Simpler, but every knob move changes the state, so every gesture would send it. Comparing hashes made a knob-only change cost nothing with the test VST3, Serum 2, Pro-Q 3 and Sylenth1, once parameter values travelled exactly.
- **Rely on the plugin's `setDirty` only.** Generic, cheap and correct when plugins call it, but nothing requires them to. Kept as one layer, not the only one.
- **Poll the state all the time.** Finds every change, but a read of a 10 MiB state took over 100 ms on the main thread, and polling cannot tell a person's edit from a plugin settling after a load. Kept, but budgeted and limited to while the window is open.
- **Merge states, or diff them.** Impossible for an opaque state without knowing each plugin's format.
- **JUCE's wrapped state, as Tracktion Engine saves it.** It wraps the plugin's bytes in XML with base64, a third larger, and gives no sign whether the plugin accepted a load. Raw bytes, as a `.vstpreset` holds them, are smaller and can be checked.
- **Refuse to sync a state that names a file.** Safer for the path rule, but it would refuse samplers and any plugin that keeps a user file, which is most of what people want synced.

## Consequences

- A preset, an LFO shape or a wavetable follows within about a second when the plugin hints or the person uses its window; a plugin that does neither is found by polling, more slowly, and an edit made in the moments after another member's state arrives, with no sign of a person, can be taken as the plugin settling (2.7 to 5.2 % of the spike's simulated runs with only `setDirty` or no signal at all, 0.9 to 2.0 % once settling is learned per plugin; none when a person's input is seen, which the app does on every platform).
- Two people changing the same plugin's hidden part at once do not merge: one wins. A hidden edit in progress is lost to a state that arrives during it, and the person is told. With Serum 2 this once left the two copies showing different LFO shapes although their saved states were equal, which the host cannot detect.
- Each state load can silence the receiving plugin for a few seconds (Serum 2: about 4 s), while the person who picked the preset in the plugin's own browser hears no gap. A knob turn does not load, but a preset or another hidden change does, and the other person hears the gap. This does not meet NFR-4 (another member's preset load sounds no worse to you than to them); loading into a second instance in the background and switching over is the likely remedy, not tried.
- The parameter wire format is bound to exactness: a format that rounds values makes every knob turn a state load.
- Loading a large state can stall the interface for a moment; the product shows progress and reads large states rarely.
- A plugin version that refuses another version's state leaves the two sounding different. The host can tell and must show it. The real pairs tried, Pro-Q 3 3.2.7.0 and 3.2.9.0 both ways and Pro-L 2 2.2.4.0 into 2.2.6.0, synced and sounded the same, so a version difference is flagged, not blocked (ADR-0010, decided 21 November 2026), with a warning on each load that is refused or differs.
- Two people on the same control: the last to let go wins, and the other sees their value replaced. Two people on different controls of one plugin both keep their edits. Seen with Pro-Q 3 and Pro-L 2.
- Holding back a preset's parameter changes until its state goes out delays them by about the quiet period, and the host must tell a preset load from a person's edits without a held control; how reliably it can is not measured.
- A knob turned while someone else's state arrives keeps the knob and takes everything else from their state (PLG-10). Until a preset travels as one unit, its parameters reach the person holding the knob at once and the rest when they let go. There is no soft lock: each sees where the other's hands are (LOB-10), and the choice is theirs. A hardware knob mapped by MIDI learn has no grab or let-go, so it must count as held while it moves (HW-3).
- Whatever a plugin saves travels, including how its window looks (Pro-Q 3's display range). Two people cannot keep different views of one plugin.
- A state may carry a person's local paths (and so their user name) to another member.
- The rules are pure and fit the TypeScript sync client beside the parameter rules; the engine host reads, loads, hashes and watches for hints.

## How we will know

In the product: a test where two presets are clicked at the same moment and one wins whole, and one where a click in the window after loading someone else's preset sends nothing back, with Serum 2. Further version pairs from #14 as they come. If real plugins rarely save the same bytes for the same content, comparing hashes saves little and every announcement means a transfer. If they rarely hint and the mouse misses their edits, detection needs another layer. If a version pair loads with a silent difference, ADR-0010 should block, not flag, for that case.
